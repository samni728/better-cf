# 测速与选择策略

## 现有 CLI 流程

当前 `main.go` 的核心流程是：

```text
读取 IP 池
-> 随机生成 100 个测试 IP
-> 并发请求测速域名 /cdn-cgi/trace，快速排除无响应 IP 并读取 CF-RAY
-> 如已选地区，按 CF-RAY 的实测响应机房筛选
-> 对剩余候选进行 3 次 RTT 稳定性测试
-> 淘汰任意 RTT 样本超过上限的 IP
-> 将全部有效候选按 RTT 从低到高排序
-> 串行速度测试
-> 对达到设置带宽的 IP 再做 3 次 RTT 复检
-> 找到带宽与 RTT 都稳定达标的 IP
-> 输出优选结果
```

CLI 当前输出包括：

```text
优选 IP
设置带宽
实测带宽
峰值速度
往返延迟
数据中心
总计用时
```

这些字段在 Web 产品中都应该作为结构化数据保存。

## Web 版需要改变的地方

Web 版不能只返回第一个达标 IP，而应该返回 Top N：

func ScanTopIPs(req ScanRequest) ([]IPTestResult, error)

核心请求：

```text

use_tls: true / false
result_count: 10

```

核心结果：

```text

rtt_ms
data_center_code
data_center_name
test_duration_seconds
passed
rank
selected_for_dns
```

## 运行模式

### 强制新扫描

默认模式。

每次都从 IP 池随机生成新候选 IP，重新 RTT 和速度测试，再选择 Top N 写入 DNS。

适合：

- 每日自动更新。
- 用户手动要求换一批新 IP。
- 当前 DNS IP 质量不稳定。

### 地区筛选

强制新扫描可以选择三种地区模式：

```text
全局随机：保留原有行为
地区优先：每次选优先测试目标国家/大区/城市，连续 10 分钟没有达标结果后回退到全局随机
严格地区：只测试目标地区，不自动回退；单个协议族连续 30 分钟没有新增有效 IP 时任务失败
```

地区筛选在候选 IP 实测响应后完成：

```text
读取原版 ips-v4.txt / ips-v6.txt
-> 从 Cloudflare Anycast 地址池随机生成候选 IP
-> 快速请求测速域名并读取 CF-RAY
-> 用 locations.json 把 CF-RAY 机房码转换为国家 / Cloudflare 大区 / 城市
-> 按用户选择过滤实际响应机房
-> 对匹配候选进行 3 次 RTT 稳定性测试和下载测速
```

严格地区下，系统先复测历史上已成功返回目标 `CF-RAY` 的具体 IP；仍满足当前 RTT、带宽和机房条件时可直接复用。其次使用这些 IP 所属 IPv4 `/24` 或 IPv6 `/48` 子网生成新 IP。扫描过程中新发现的地区匹配 IP，即使带宽暂时不达标，其子网也会立即进入后续扩展池。同时原版全局地址池按随机顺序无重复遍历，完整遍历一轮后才重新洗牌。

`local-ip-ranges.csv` 是 Cloudflare GeoFeed 地理标注数据，不是原版 better-cloudflare-ip 的可测 CDN 候选池。将它直接用于生成候选，会产生大量无法响应当前测速域名的 IP。Cloudflare 是 Anycast 网络，同一 IP 从不同测试机出发可能路由到不同机房，所以“日本”等条件必须以当次响应的 `CF-RAY` 为准。

WebUI 会实时显示当前国家、大区和城市匹配的 Cloudflare 响应机房数量与 IATA 代码。更改地区或模式后必须保存配置，后续“立即执行”和定时任务才会使用新值；每条运行记录会显示任务创建时冻结的实际配置。

当 IPv4 和 IPv6 同时启用时，某一协议族连续 30 分钟无新增结果只会结束该协议族，不会提前结束整个任务。系统会继续执行另一协议族，最后统一检查 IPv4 / IPv6 数量。只有所有已启用协议族都收集满时才会替换 DNS，避免部分结果覆盖正在使用的完整记录。

### 重测当前 IP

辅助模式。

从当前 Cloudflare DNS 读取指定域名下的 A / AAAA 记录，只重测这些 IP 的 RTT、速度和数据中心。

适合回答：

```text
当前正在使用的 IP 现在还快不快？
这个 IP 已经连续通过几天？
是否需要强制换新？
```

### 补位扫描

第二阶段再做。

先重测当前 IP，如果通过数量不足，再扫描新 IP 补足缺口。

## 通过标准

一个 IP 通过测试的最低标准：

- RTT 测试成功。
- 测速前后各 3 次 TCP RTT 样本均不超过用户设置的最大 RTT。
- 能通过 HTTP / HTTPS 请求验证 Cloudflare 响应。
- `peak_speed_kbps > 0`。
- `measured_bandwidth_mbps >= configured_bandwidth_mbps`。
- 能解析出数据中心更好，但不作为硬性条件。

## 排序策略

MVP 先使用透明排序，不引入复杂黑盒评分。

排序优先级：

1. 通过测试的 IP 优先。
2. 实测带宽越高越好。
3. 峰值速度越高越好。
4. RTT 越低越好。
5. 历史连续通过天数越多越好。
6. 最近被成功同步过的 IP 可作为稳定性参考，但强制新扫描模式下不强行偏向旧 IP。

## 指标解释

### 设置带宽

用户期望的最低带宽，例如 100 Mbps。

当前 CLI 中换算为：

```go
speedKB := bandwidthMbps * 128
```

### 实测带宽

根据峰值速度换算：

```go
measuredBandwidthMbps := peakSpeedKBps / 128
```

### 峰值速度

下载测速过程中按 1 秒窗口统计的最大速度，单位 kB/s。

### RTT 延迟

TCP 连接耗时，不是 ICMP Ping。候选 IP 在下载测速前后各连续测试 3 次；任意样本超过最大 RTT 即淘汰，最终记录两轮中较差的平均值。这样既保留带宽要求，也避免选中瞬时连接快、随后响应明显变慢的 IP。

### 可选真连接测试

真连接测试是原扫描流程之后的附加准入条件，不等于 TCP RTT，也不等于下载测速。系统使用用户分别提供的 HTTP/非 TLS 与 HTTPS/TLS `vmess://` 或 `vless://` 模板，把服务器地址和端口替换为当前候选 Cloudflare IP/端口，再通过临时 Xray 代理访问测试 URL。

IPv4、IPv6、HTTP 和 HTTPS 均可独立勾选。HTTP 检查 `80, 8080, 8880, 2052, 2082, 2086, 2095`，HTTPS 检查 `443, 2053, 2083, 2087, 2096, 8443`。系统完整测试已选端口组；至少一个端口返回 `2xx/3xx` 才保留候选，并保存全部通过端口及各自响应延迟。全部端口失败时继续扫描下一个候选，直到达到结果数量或触发现有协议族无新增结果超时。

### 数据中心

从 `CF-RAY` 响应头中提取三字码，再通过 `locations.json` 转换为城市名。

## 历史画像

### Now：SQLite 搜寻记忆

Web 服务现在使用 `data/search_memory.sqlite` 保存搜寻经验，JSON 状态文件继续保存产品配置、任务记录和最终结果。两者职责分开，避免为了候选调度一次次改写整份 JSON。

记忆以“IP 版本 + 地区策略 + 带宽/RTT 门槛 + 真连接 HTTP/HTTPS 节点指纹 + 测试 URL”为 profile。更换节点或测试条件会形成新的记忆空间，不会把旧节点的失败错误继承给新节点。节点原文不会写入 SQLite，只保存不可逆指纹。

候选顺序：

```text
同 profile 的真连接成功 IP 复测
-> 成功 IP 所在 /24（IPv6 /48）深挖
-> 成功 IP 所在父 /16（IPv6 /32）探索
-> 原版 Cloudflare 全局地址池的新网段
```

- 3 天内成功为新鲜经验，权重最高。
- 3–7 天成功仍可作为较弱线索；超过 7 天不再参与候选调度。
- 真连接失败的具体 IP 冷却 3 天，跨任务和服务重启仍有效。
- 同一 IPv4 `/24`（IPv6 `/48`）在 24 小时内至少 8 个不同 IP 真连接失败且没有成功时，整个网段冷却 24 小时。
- 每个 HTTP/HTTPS 端口独立记录成功、延迟和错误类别，便于区分超时、拒绝、TLS/WS 握手和 EOF。
- 旧 `app_state.json` 的测速结果只导入为 `scan_success_unverified`，不会被误认为已经通过真连接。

每次找到新真连接成功 IP 后，本次任务会立即把它的窄网段和父网段加入后续候选；同一任务内的新失败 IP 也会立即跳过。

### v1.1.0 自适应预算与分析

每次真连接观察会记录候选来源：`exact`、`narrow`、`wide`、`global`。系统对近 7 天成功率做 Beta 平滑，保留每类最低探索预算，再把剩余 40% 按平滑成功率分配。默认无样本时使用：

```text
历史精确 IP 15%
窄网段 /24（IPv6 /48）30%
父网段 /16（IPv6 /32）20%
全局探索 35%
```

任何类别都不会因为短期失败被永久归零，全局探索始终保留最低预算，避免历史经验形成封闭循环。设置页可以为单个 profile 手动增加 IPv4 `/16` 或 IPv6 `/32`；手动网段进入父网段候选池，但仍受真实 RTT、带宽、CF-RAY 和真连接门槛约束。

设置页同时展示：

- 近 7 天成功网段、冷却网段和采样覆盖率。
- 每个端口的尝试数、成功率与成功样本平均延迟。
- 测试出口/运营商标签，便于多个运行出口的结果分开阅读。
- HTTP 有成功端口、HTTPS 已测试但全部失败的窄网段特征。

每个 IP 需要积累长期画像：

```text
首次发现时间
首次写入 DNS 时间
最近测试时间
最近写入 DNS 时间
测试次数
通过次数
失败次数
被选中次数
连续通过天数
历史最佳带宽
历史最佳峰值速度
历史最佳 RTT
最近数据中心
```

这样 WebUI 可以展示：

```text
这个 IP 已经用了 7 天
连续 7 天测试通过
历史最佳 124 Mbps
最近一次 104 Mbps
数据中心 Los Angeles
```
